# ADR-005 - Oracle Identity Strategy

# Lesson 9 - ADR

**Status:** Accepted

**Date:** 2026-07-11

## Decision

The Employee Leave Management System will use Oracle identity columns for database-generated surrogate identifiers.

Surrogate identifier columns should use the repository standard `NUMBER(19)` data type and Oracle identity generation in table DDL. Unless a table-specific design requires a stricter rule, identity columns should use `GENERATED BY DEFAULT ON NULL AS IDENTITY` so Oracle can generate identifiers while still allowing controlled data migration or repair scripts to provide explicit values when necessary.

This decision applies to internal surrogate identifier columns such as `EMPLOYEE_ID`, `LEAVE_TYPE_ID`, and `LEAVE_REQUEST_ID`. It does not create primary key constraints, foreign key constraints, unique constraints, indexes, seed data, or migration tooling by itself.

## Context

The Employee Leave Management System uses Oracle 26ai as the confirmed database platform and Spring JDBC (SimpleJdbcCall) as the confirmed data access approach.

The repository standards require meaningful Oracle object names, `NUMBER(19)` for identifiers, and Oracle naming conventions for database objects. The same standards also state that primary key strategy and Oracle-specific feature usage should remain **To Be Decided** until confirmed.

The project needs a consistent strategy for generating internal surrogate identifiers before physical table DDL is finalized. Employee numbers, leave type codes, request numbers, and other business-facing values can change or follow business-specific formats, so they should not be used as the internal row identity strategy.

## Alternatives Considered

### Identity Columns

Oracle identity columns generate numeric identifiers directly from the table definition. This keeps identifier generation close to the table, avoids separate sequence objects for ordinary surrogate keys, and fits the repository standard that identifiers use `NUMBER(19)`.

### Sequences

Standalone Oracle sequences are a proven identifier strategy and remain useful when a future design needs shared numbering, custom allocation, or sequence reuse outside a single table. If sequences are introduced later, they must follow the repository naming standard `LMS_SEQ_<TABLE_NAME>`.

Sequences are not selected as the default strategy because ordinary table-specific surrogate keys do not currently require separate sequence objects.

### `SYS_GUID()`

`SYS_GUID()` can generate globally unique RAW values, but it does not align with the repository standard that identifiers use `NUMBER(19)`. It is also less convenient for the current Spring JDBC (SimpleJdbcCall) and Oracle table designs, which use numeric surrogate identifiers.

`SYS_GUID()` is not selected for primary surrogate identifiers.

## Rationale

Oracle identity columns provide the simplest default strategy for table-local surrogate identifiers in Oracle 26ai while staying aligned with the repository standards.

Using `NUMBER(19)` identity columns keeps identifier types consistent across tables, supports straightforward Spring JDBC (SimpleJdbcCall) mapping to numeric application identifiers, and avoids introducing extra sequence objects before there is a confirmed need for them.

`GENERATED BY DEFAULT ON NULL AS IDENTITY` is preferred over `GENERATED ALWAYS AS IDENTITY` because it gives the project a practical path for controlled data movement, restore scenarios, or administrative repair scripts without disabling the database-generated default behavior for normal inserts.

## Consequences

Positive consequences:

- New table DDL can use a consistent identity strategy for surrogate identifier columns.
- Identifier columns remain numeric and aligned with the `NUMBER(19)` repository standard.
- Ordinary inserts can omit surrogate identifier values and let Oracle generate them.
- The project avoids creating separate sequence objects unless a later table-specific requirement justifies them.

Tradeoffs and constraints:

- Existing table DDL created before this ADR may need to be updated to add identity clauses.
- Identity columns are table-local; they should not be used for shared business numbering requirements.
- Explicit identifier inserts should be limited to controlled migration, restore, or repair scenarios.
- Business identifiers such as employee numbers, leave type codes, and request numbers still need separate business rules and validation.

Still To Be Decided:

- Primary key, foreign key, unique constraint, and index definitions for each table.
- Migration tooling and deployment process for database schema changes.
- Seed data format and data loading approach.
- Whether any future table needs a standalone sequence for a table-specific or business-numbering reason.
